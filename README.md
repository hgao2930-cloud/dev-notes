## 1. Express 路由参数：res 被当成了 req

**问题**

点「退出登录」没反应，页面上也没有任何报错提示；只有打开 Network 才看到接口返回了 500。去后端看日志，真正的报错是 `res.clearCookie is not a function`。

**原因**

Express 的路由处理函数接收的是 `req、res、next` 三个参数，顺序不能错：分别对应请求对象、响应对象，以及交给下一个中间件处理的函数。用不到的参数不能直接省略，否则后面的参数会整体前移；可以用 `_req` 这种名字占住参数位置。

**解决办法**

用 `_req` 占住第一个参数位置：

`(_req, res) => { ... }`

**深入思考**

Express 对参数的处理和 JS 里的函数是一样的，参数按位置匹配，不是一个实例上的三个属性。所以少写一个参数，后面的参数就会整体前移。

## 2. 滚到底加载下一页时，切分类会串数据

**问题**

做代码审查时发现一个场景：如果第二页的请求还在路上时切换了分类，等这个旧请求返回，它会把上一个分类的商品**追加**到已经换过的列表里；同时页码被多加一次，导致跳页——某些商品怎么翻都出不来。

（这个问题没在页面上实际碰到过，是审查推演 + 最小 demo 验证出来的。）

**原因**

两个原因叠加：

1. 请求的返回顺序和发出顺序不一定一致；
2. 我在请求下一页的函数里，直接把返回的数据 `push` 到了当前列表上，而这个列表在切换分类时已经换成了新分类的数据，所以旧分类的请求回来后还能修改现在的列表。当时也没有判断这个响应是不是已经过期。

页码也一样：旧请求回来后仍然继续走后面的状态更新逻辑，就可能把已经切换分类后的页码再加一次。

**解决办法**

给每次请求加一个 id。

发起请求时，把当前的 id 保存到这次请求自己的局部变量里；请求还在途时如果又发起了新的请求，全局 id 就会变化，但之前请求保存的那个 id 不会跟着变。

响应回来时，如果它保存的 id 和当前全局 id 不一致，就说明这个响应已经过期，直接丢弃，不让它修改当前列表和页码。

**深入思考**

以前比较容易把“请求发出顺序”和“请求处理顺序”看成一回事，但异步请求不能这样假设。真正需要判断的是：**这个响应回来时，它还是不是当前这次操作对应的响应。**

## 3. 并发下单：库存被扣成负数，后来又遇到死锁

**问题**

两个请求同时买最后一件商品，库存被扣成了负数。加了事务之后又出现另一个问题：两笔订单包含相同的商品、但顺序不同，它们互相等对方持有的锁，最后其中一个被数据库回滚，前端收到 500。

**原因**

最初用的是先查询后更改的写法，也没有加入事务。原因主要是如果用 `SELECT` 查询到的数据来处理逻辑，会出现同时两笔扣库存的查询，此时两笔都查到了有库存，就同时触发扣库存的查询，扣库存的时候又没有做条件校验，就会出现负库存的问题。

加上事务能保证扣库存和下单在**同一个事务**中，要么一起提交，要么一起回滚，尽量避免出现扣了库存没下订单、或者下了订单库存却没扣的问题。但要注意，`rollback` 本身也是连接数据库进行的异步操作，也有失败的可能，所以不能让回滚时的新错误把原来的错误覆盖掉。

死锁是因为多个事务操作多行数据时会持有行级锁。如果两笔事务加锁的顺序相反，就可能出现一笔先锁 A 再锁 B，另一笔先锁 B 再锁 A，最后互相等待对方释放已经持有的锁，形成循环等待。数据库检测到死锁后，会回滚其中一个事务。

**解决办法**

**超卖**：不要「先查再改」，把库存校验直接写进 `UPDATE`：

`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`

这样库存检查和扣减在一次更新中完成，再通过 `affectedRows === 0` 判断库存不足。

**死锁**：把请求里的商品按 id 排序后再依次处理，让不同事务按照相同的顺序加锁，避免因为加锁顺序不同产生循环等待。

## 4. 无限滚动的哨兵：视口、DOM 存在性与 v-for 重建

**问题**

1. 列表底部放一个空 `div` 当哨兵，它进入视口就加载下一页。

一开始哨兵放在列表容器里面，数据还没加载出来时它根本不在 DOM 里，`ref` 也拿不到；后来放到容器外面才正常工作。

2. 从「全部」切到商品很少的分类后，页面被顶到了最底部，哨兵明明就在视口里，但「加载更多」再也不触发了。

**原因**

1. 如果哨兵本身跟着列表内容一起创建，而初始状态下列表还没有对应内容，那么这个 DOM 节点根本还不存在，自然也拿不到它对应的 `ref`。

2. 切换分类时，列表数据整体被替换。原来的列表比较长，新的列表比较短，但浏览器的滚动位置并不会因为数据换了就自动回到顶部，所以新的内容可能直接把当前滚动位置顶到了底部。

这时候哨兵已经处在视口内，但 `IntersectionObserver` 关注的是交叉状态的变化。它如果已经是「在视口内」的状态，后面没有再次发生进入/离开视口的变化，就不会因为“还在视口里”一直触发回调，所以加载更多就停住了。

**解决办法**

1. 把哨兵放到不会因为列表数据为空而一起消失的位置，保证需要观察时它已经存在于 DOM 中。

2. 切换筛选、列表数据更新之后，把滚动位置重置到顶部：

`window.scrollTo({ top: 0 })`

这样新的列表从顶部开始，哨兵重新经过「不在视口 → 进入视口」的过程，就可以正常触发加载。

**深入思考**
或许可以用虚拟滚动来避免数据切换的时候视口乱跳，但是数据量少的时候没啥必要
