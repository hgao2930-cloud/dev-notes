## 一、异步请求与状态变更的竞态

**典型场景**：列表分页加载、搜索、筛选切换——凡是「请求内容依赖可变状态」的地方。

**问题的本质**

- 网络请求的返回顺序不确定，先发出的请求可能后返回
- 「状态已经改变、旧请求还在途中」存在一个窗口，旧响应回来时会写入已经过期的数据

**可复用的做法**

| 手段 | 作用 |
|---|---|
| 请求序号（代次） | 条件变化时递增；响应回来先比对，不是最新的直接丢弃 |
| 参数快照 | 请求发出时固定参数，避免异步过程中读到被改过的状态 |
| 加载互斥守卫 | 正在重新加载时，不允许触发「加载更多」这类追加请求 |
| 数据分层 | 接口响应只读；列表状态独立维护；派生数据用 computed |

**自检问题**

- 这个请求依赖的状态，在它返回之前会不会被改？
- 如果被改了，这个旧响应还会写数据吗？
- 「接口响应」和「页面列表」是不是同一个变量？（是的话就有隐患）

**相关细节**：为什么「参数比对」不能替代序号（相同参数也可能先后发出）；切换筛选后需要重置滚动位置。

## 二、数据库并发：原子性、行锁与死锁

**典型场景**：库存扣减、余额、计数等「读-改-写」操作；一个事务里更新多行。

**问题的本质**

- 「先查再写」是两条语句，中间有窗口，并发下会超卖或覆盖
- 事务中的行锁如果加锁顺序不一致，会形成循环等待 → 死锁

**可复用的做法**

| 场景 | 做法 |
|---|---|
| 单个数值的「检查 + 扣减」 | 条件更新：`UPDATE ... WHERE id = ? AND stock >= ?`，用 `affectedRows === 0` 判定失败 |
| 「存在则累加、不存在则插入」 | `INSERT ... ON DUPLICATE KEY UPDATE`（依赖唯一键，一条语句完成判断与写入） |
| 一次更新多行 | 固定加锁顺序（按主键排序后再操作） |
| 事务收尾 | `rollback` 包 try/catch（避免回滚错误盖掉原始错误）；`release` 放 finally |

**自检问题**

- 这个操作能不能用一条 SQL 表达「检查 + 写入」？（能就不要分两步）
- 批量操作有没有固定的加锁顺序？
- 事务边界是否覆盖了所有「必须一起成功或一起失败」的操作？

## 三、DOM 生命周期与浏览器观察机制

**典型场景**：无限滚动、图片懒加载、进入视口触发动画。

**问题的本质**

- 元素是否存在取决于渲染条件（`v-if` 为假时它根本不在 DOM 里）
- 观察者（如 `IntersectionObserver`）只在**状态发生变化**时回调，不是持续触发
- `v-for` 更新会销毁重建 DOM，旧的观察目标随之失效

**可复用的做法**

- 观察目标放在**稳定**的位置：不要放进条件分支，也不要放进 grid / flex 这类会参与布局的容器
- 数据变化后主动重新评估一次（`nextTick` 后 `unobserve` + `observe`，或手动判断位置）
- 内容高度会变化时，注意滚动位置（切换数据源后重置到顶部）

**自检问题**

- 观察时这个元素在 DOM 里吗？数据变化后它还是同一个元素吗？
- 元素明明在视口里却一直不触发，是不是因为「没有新的状态变化」？

## 四、前后端契约与信任边界

**典型场景**：订单金额、状态流转、权限判断等「不能只信客户端」的数据。

**问题的本质**

- 客户端传什么都可以被改（改请求参数、直接用工具调接口）
- 历史数据要在来源变化后仍然能复原（商品改价、下架、用户改地址）

**可复用的做法**

| 做法 | 解决什么 |
|---|---|
| 服务端重算金额 | 防止客户端篡改价格 |
| 保存数据快照 | 商品改价 / 下架后，历史订单仍然准确 |
| 状态机在服务端校验 | 防止客户端直接跳到非法状态 |
| 错误语义分层 | 业务错误（带状态码，如库存不足 409）与系统错误（500）分开：前者返回明确信息，后者只记日志 |
| 按用户校验归属 | 每个接口只返回 / 只操作当前用户的数据，防止越权 |

**自检问题**

- 这个值如果被客户端改掉，业务上会发生什么？
- 一年后原始数据变了，这条记录还解释得清吗？

## 附：具体案例速查

一些具体的坑，一行一条，方便快速回忆：

- **Express 路由按位置传参**：第一个参数永远是 `req`；用不到的参数也要用 `_req` 占位，否则 `res` 拿到的会是 `req`
- **Vue 的 `ref`**：模板里自动解包，`<script>` 里必须写 `.value`；`reactive` 不需要
- **grid 容器**：会把直接子元素当成网格项，非内容元素（哨兵、占位）要放在容器外
- **`finally` 里不要 `return`**：会吞掉异常，改成条件赋值
- **接口响应**：不要当累加器用（`push`），它只是某一次请求的快照
- **唯一键**：既是业务约束，也是 `ON DUPLICATE KEY UPDATE` 的触发条件
