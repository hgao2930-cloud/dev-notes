## 1. Express 路由参数：res 被当成了 req

**问题**

点「退出登录」没反应，页面上也没有任何报错提示；只有打开 Network 才看到接口返回了 500。去后端看日志，真正的报错是 `res.clearCookie is not a function`。

**原因**

Express 的路由处理函数接收 `(req, res, next)` 三个参数，顺序不能错：分别对应请求对象、响应对象、以及交给下一个中间件的方法。用不到的参数不能直接省略（省略后后面的参数会整体前移），但可以用 `_req` 这种带下划线前缀的名字占位。

**解决办法**

用 `_req` 占住第一个参数位置：`(_req, res) => { ... }`

**深入思考**

Express 对参数的处理和普通 JS 函数一样：参数按位置匹配，不是对象上的属性——所以少写一个参数，后面的参数就整体前移了。

## 2. 滚到底加载下一页时，切分类会串数据

**问题**

做代码审查时发现一个场景：如果第二页的请求还在路上时切换了分类，等这个旧请求返回，它会把上一个分类的商品**追加**到已经换过的列表里；同时页码被多加一次，导致跳页——某些商品怎么翻都出不来。

（这个问题没在页面上实际碰到过，是审查推演 + 最小 demo 验证出来的。）

**原因**

两个原因叠加：

1. 请求的返回顺序和发出顺序不一定一致；
2. 我在请求下一页的函数里，直接把返回的数据 `push` 到了「当前列表」上——而这个列表在切换分类时已经被换成了新分类的数据，所以旧分类的商品被追加了进去。当时也没有判断「这个响应是不是已经过期了」。

**解决办法**

给每次请求记一个 id，和「当前最新的 id」比对：

- 发起请求时，把当前的 id 存进这次请求的作用域（它在本次请求的生命周期内不会变）；
- 如果请求还在路上时又发起了新请求，全局 id 会变；
- 响应回来时，它记录的 id 和全局 id 不一致，就说明这个响应已经过期，直接丢弃、不写进列表。

**深入思考**

（可以想一想：为什么不能只比较「参数」来判断响应是否过期？）

## 3. 并发下单：库存被扣成负数，后来又遇到死锁

**问题**

两个请求同时买最后一件商品，库存被扣成了负数。加了事务之后又出现另一个问题：两笔订单包含相同的商品、但顺序不同，它们互相等对方持有的锁，最后其中一个被数据库回滚，前端收到 500。

**原因**

**超卖**：一开始用的是「先 SELECT 查库存、再 UPDATE 扣减」的写法，而且没有事务。两个请求并发时会同时读到「有库存」，于是都执行了扣减；而扣减语句本身没有校验，结果扣成了负数。

加上事务之后又明白了两件事：

- 事务能保证「扣库存 + 创建订单」要么都成功、要么都失败，避免「扣了库存没下单」或「下了单但库存没扣」；
- `rollback` 本身也是要连数据库的异步操作，也可能失败，所以要包在 try/catch 里，而且不能用它的错误盖掉原始错误。

**死锁**：InnoDB 修改数据时会加行级锁。如果两笔请求对多行的加锁顺序相反（一个先锁 A 再锁 B，另一个先锁 B 再锁 A），就会互相等对方释放，形成循环等待；等到超时，数据库会回滚其中一笔。

**解决办法**

- **超卖**：不要「先查再改」，把校验写进更新语句——`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`，靠行级锁让「检查 + 扣减」成为一次原子操作；再用 `affectedRows === 0` 判断库存不足。
- **死锁**：把要扣的商品按 id 排序后再依次扣减，让所有事务用同一个顺序加锁，从源头避免「互相等待」。

**深入思考**

- 排序的代价不是「慢」（内存里排几十条可以忽略），而是顺序统一之后，同一批商品的并发会排队——但事务很短，这点吞吐损失可以接受。
- 死锁没法靠排序完全避免（还有别的场景），所以应用层最好能识别死锁错误并允许重试。

## 4. 切换分类后，「加载更多」不再触发

**问题**

列表是「滚到底部自动加载下一页」，列表底部放一个空 `div`（哨兵），它进入视口就请求下一页。

从「全部」切到商品很少的分类后，页面被顶到了最底部；哨兵明明就在视口里，但「加载更多」再也不触发了，只能看到第一页的数据。

**原因**

两件事叠在一起：

1. 切换分类时列表数据整体被替换。新分类的数据比原来少，浏览器的滚动位置还停在原处，但内容撑不住这么高，就被「顶」到了页面最底部；
2. `IntersectionObserver` 只在**交叉状态发生变化**时回调（从「不在视口」到「在视口」，或者反过来）。哨兵一直待在视口里，没有发生状态变化，就不会再触发回调，加载更多就停住了。

**解决办法**

切换筛选、列表数据更新之后，把滚动位置重置到顶部：`window.scrollTo({ top: 0 })`。

**深入思考**

浏览器会尽量维持滚动位置，所以内容越长，切换数据后的位置偏移越明显。顺着这个思路还有另一个方向：不要一次渲染全部数据，只渲染视口需要的部分、上下各留一点缓冲（也就是虚拟滚动的思路）——不过商品列表是响应式 grid、列数不固定，虚拟滚动算不准偏移，所以这里用「分页 + 无限滚动 + 重置滚动位置」更合适。
