# 数据库行锁：条件更新防超卖、固定顺序防死锁

## 现象一：并发下单超卖

（两个人同时买最后一件商品，库存被扣成负数）

## 根因

（先 `SELECT` 查库存、再 `UPDATE` 减库存，是两条语句，中间存在时间窗口——两个请求都读到"库存够"，于是都执行了扣减）

## 解决

（改成条件更新：`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`，用 `affectedRows === 0` 判定库存不足。检查与扣减在**同一条 SQL** 内完成，由 InnoDB 的行锁保证原子性）

## 现象二：并发下单死锁

（两笔订单包含相同商品但顺序不同，互相等待对方的行锁；MySQL 检测到死锁后回滚其中一个事务，客户端收到 500）

## 根因

（加锁顺序不确定会形成「循环等待」——死锁的四个必要条件之一）

## 解决

（扣库存前先按商品 id 排序，让**所有事务按同一顺序**申请锁，从源头破坏循环等待）

## 教训

（行锁既是并发安全的基础，也是死锁的来源；事务里要控制加锁顺序；死锁发生时数据库会回滚一个事务，客户端应当可以重试）

## 延伸

（死锁的四个必要条件；`SELECT ... FOR UPDATE` 和条件更新的取舍；为什么 `rollback()` 要包 try/catch 并保留原始错误）
